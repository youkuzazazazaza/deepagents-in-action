# 03-03 大结果治理：截断 vs 卸载（Agent 的"防洪系统"）

> 对应实验：`code/lab3_eviction.py` ｜ 证据：`evidence/lab3_out.txt`、`evidence/lab3_evidence.json`

## 一、人话开场：工具吐回来一座山怎么办？

Agent 调工具经常"挖矿挖出整座山"：一个 `execute` 跑 `cat huge.log`、一个搜索工具返回 200 条结果……
如果原样塞回上下文，几个大结果就能把窗口撑爆——这就是"工具结果洪峰"。

deepagents 的防洪系统有**两道闸门**，分工明确：

| | 闸门 A：就地截断 | 闸门 B：卸载转存 |
|---|---|---|
| 谁触发 | `read_file` 自己 | 除 read_file 外的**任意**工具（含 execute、自定义工具） |
| 怎么处理 | 砍到额度内，尾部贴"已截断"提示 | 全文存进 `/large_tool_results/<call_id>`，原地只留一张"取件条" |
| Agent 能拿回全文吗 | 能，但要带 offset/limit 分段再读 | 能，拿着取件条去 read_file（也要分段） |

**红线在哪？（源码推导）**

```python
NUM_CHARS_PER_TOKEN = 4                      # 1 token ≈ 4 字符（保守估计）
tool_token_limit_before_evict = 20000        # 默认 2 万 token
红线 = 20000 × 4 = 80000 字符
```

## 二、Lab3 实验设计

**A 段（截断）**：预置一个 4000 行、223,999 字符的 `/workspace/big.md`，让 Agent `read_file(offset=0, limit=4000)` 一次读完。
**B 段（卸载）**：注册自定义工具 `get_server_log`（返回 2000 行、约 13 万字符的假日志），让 Agent 回答"最后一条日志的 job 编号"——**答案在文件尾部**，Agent 想答对就必须走"卸载→按需读回"的完整闭环。

## 三、实测结果（数字全是真实 trace）

**A 段：**

```text
预置大文件 big.md：223999 字符（红线 80000）
tool read_file  返回  79965 字符     ← 卡着 80000 红线砍的！
截断标记出现: True
Agent 总结: 我实际只收到了 1283 行（不是 4000 行），内容止于 LINE-01282
末尾提示原文: [Output was truncated due to size limits. The file content
              is very large. Consider reformatting the file ...]
              [Read 1283 lines (lines 1-1283 of 4000) ...]
```

**B 段（完整闭环跑通）：**

```text
tool get_server_log  返回  1377 字符  ← 13 万字符被换成一张"取件条"！
tool read_file       返回   719 字符  ← Agent 自己去分段读尾部

--- 取件条原文（前 600 字符）---
Tool result too large, the result of this tool call call_00_fc0v... was saved
in the filesystem at this path: /large_tool_results/call_00_fc0v...
You can read the result from the filesystem by using the read_file tool,
but make sure to only read part of the result at a time. ...
Here is a preview showing the head and tail of the result ...

虚拟磁盘里多出来的卸载文件:
  /large_tool_results/call_00_fc0vhX13wxwNBwHrkGZM5052 (131696 chars)

Agent 最终回答: 最后一条日志的 job 编号是 01999 ✓✓✓
```

**看点**：13 万字符的洪峰，上下文里只进了 1377+719 ≈ 2K 字符，但答案照样答对——这就是"防洪不丢信息"的精髓。

## 四、两个藏在细节里的魔鬼

**魔鬼 1：read_file 不带 limit 时默认只读 100 行！**
我第一版实验让 Agent"不带参数直接读"，结果只回了 6184 字符、无截断标记——因为默认 `limit=100` 根本够不到红线。
**要演示截断，必须显式给大 limit。** 这本身也是重要的工程知识：别指望"一次 read_file 全读出来"，要么分页，要么明确 limit。

**魔鬼 2：预置文件必须用 `{"content": ...}` 字典**（03-01 已提），纯字符串直接 `TypeError: string indices must be integers`。

## 五、源码考古路线图（想深挖的照此路径读）

```
middleware/filesystem.py
 ├─ NUM_CHARS_PER_TOKEN = 4                       (≈L905)
 ├─ _large_tool_results_prefix = f"{root}/large_tool_results"
 ├─ read_file handler → _truncate()               超红线就地砍+贴 READ_FILE_TRUNCATION_MSG
 └─ wrap_tool_call()                              通用闸门：除 read_file 外所有工具
     └─ 超红线 → 落盘 /large_tool_results/<call_id> → 替换成 TOO_LARGE_TOOL_MSG
middleware/_message_eviction.py                   两套机制共用的"头+尾预览"工具函数
```

一句话总结架构：**read_file 是"自家的娃"就地管教；其它工具是"外来的客"东西寄存前台**。

## 六、大白话复盘

- **为什么 read_file 特殊？** 因为它天生带 offset/limit 分页参数，截断后 Agent 有官方姿势拿回剩余部分；别的工具没有分页参数，只能"寄存+取件条"。
- **取件条上为什么印头尾预览？** 让 Agent 不用白跑一趟——扫一眼预览可能直接就有答案（比如"只要开头 3 行"）。
- **面试金句**："deepagents 用 2 万 token × 4 字符的估算红线，把大工具结果从上下文卸载到虚拟文件系统，实现了无损防洪。"
