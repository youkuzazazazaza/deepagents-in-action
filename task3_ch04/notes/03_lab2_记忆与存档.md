# 03 · Lab2：todos 的"失忆症"与存档机（Checkpointer + thread_id）

> 对应代码 `../code/lab2_todo_persistence.py`，证据 `../evidence/lab2_out.txt`

## 一、先抛问题

lab1 里 todos 存进了 Agent State。那第二次 invoke 时，Agent 还记得自己的计划吗？三个实验给出三种命运：

| 实验 | 配置 | 结局 |
|---|---|---|
| 实验一 | 不配 Checkpointer，连 invoke 两次 | **失忆**：第 2 次后 `todos = null` |
| 实验二 | InMemorySaver + `thread_id='user-001'` | **记得**：消息 8 条 → 17 条，todos 全程在续跑 |
| 实验三 | 换 `thread_id='user-002'` | **新开档**：全新 2 条消息，无 todos |

## 二、实验一：Agent State 是"一次性"的

```python
agent = create_agent(model, tools=[shout], middleware=[TodoListMiddleware()])
r1 = agent.invoke({"messages": [{"role": "user", "content": "建计划并做第1步"}]})
# r1['todos'] = [早安 completed, 午安 pending, 晚安 pending]  ← 有计划

r2 = agent.invoke({"messages": [{"role": "user", "content": "继续第2步"}]})
# r2['todos'] = None  ← 计划没了！
```

大白话：**每次 invoke 都是一次"新的生命"**。状态字典在函数返回后就被扔掉，第 2 次 invoke 从空白开始——它根本不知道有过计划。第 2 次的输出也能看出模型在"装懂"：它没报错，但它其实不知道"第 2 步"是什么。

## 三、实验二：Checkpointer = 存档机，thread_id = 存档槽位

```python
from langgraph.checkpoint.memory import InMemorySaver
agent = create_agent(model, tools=[shout], middleware=[TodoListMiddleware()],
                     checkpointer=InMemorySaver())
cfg = {"configurable": {"thread_id": "user-001"}}

agent.invoke({"messages": [q1]}, cfg)   # 第1轮：建计划做第1步
agent.invoke({"messages": [q2]}, cfg)   # 第2轮：做第2步（同 cfg！）
```

实测快照（用 `agent.get_state(cfg)` 看存档内容）：

```
第1轮后: n_messages=8, todos=[早安 completed, 午安 pending, 晚安 pending]
第2轮后: n_messages=17, todos=[早安 completed, 午安 completed, 晚安 completed]
```

模型完全记得计划——8 条消息里带着 write_todos 的调用记录，第 2 轮直接接着干。

机制大白话：Checkpointer 在**每个超级步（superstep）之后**把整个 State（messages + todos + ...）拍快照存起来；下次 invoke 带同一个 thread_id，就先把快照恢复进内存再跑。**像游戏存档**：进度全在，读档继续。

## 四、实验三：换个 thread_id = 插新的记忆卡

```python
cfg2 = {"configurable": {"thread_id": "user-002"}}
agent.invoke({"messages": [{"role": "user", "content": "我们的计划进行到哪一步了？"}]}, cfg2)
# get_state(cfg2): n_messages=2, 无 todos
```

同一个 agent 进程里，user-002 是全新档案。哪怕 user-001 的存档就在隔壁，模型也看不见——**多用户隔离就是这么来的**：一人一个 thread_id，互不打扰。

## 五、一张表总结三种"记忆命运"

| 配置 | 状态存哪 | 进程内多轮 | 进程重启后 | 多用户隔离 |
|---|---|---|---|---|
| 无 Checkpointer | 内存里，invoke 完即扔 | ✗ 失忆 | ✗ | ✗ |
| InMemorySaver | 进程内哈希表 | ✓ | ✗ 全丢 | ✓（靠 thread_id） |
| SqliteSaver/PostgresSaver | 磁盘/数据库 | ✓ | **✓** | ✓ |

> 第 8 章细讲 SqliteSaver：`pip install langgraph-checkpoint-sqlite`，一行换掉 InMemorySaver，重启进程存档还在。**生产必换**——InMemorySaver 是"游戏机不关机的存档"，一断电就没了。

## 六、lab2 期间踩的坑（真实翻车记录，值得学）

写快照函数时我犯了经典 bug：`snap()` 函数里写死了读 `cfg`，实验三传了 `cfg2` 但打印的还是 user-001 的状态——第一版输出"新线程 17 条消息全 completed"，差点得出"thread_id 没用"的**错误结论**。

教训：**做对照实验时，所有"读状态"的代码必须参数化，绝不能有隐式写死的全局配置**。修好后实验三立刻变成教科书结果（2 条消息、无 todos）。写课件的人也会翻车，翻车记录本身也是课程的一部分。
